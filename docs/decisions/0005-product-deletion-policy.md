# 0005. 상품 삭제/수정 정책

## 상태
확정

## 배경
중고거래 특성상 한 상품은 한 번만 거래되고 끝나는 구조라, 쇼핑몰처럼
같은 상품을 반복 판매하는 경우가 없음. 이 특성을 고려해 삭제/수정을
어떤 기준으로 제한할지 결정이 필요했음.

## 고민한 선택지
1. 모든 삭제를 소프트 삭제로 일괄 처리
2. 상품 상태 및 구매 요청 존재 여부에 따라 하드 삭제/소프트 삭제/삭제 불가를 구분

## 결정
2번 채택. 구체적으로:
- `판매중` + 구매 요청 없음 → 하드 삭제 허용
- `판매중` + 구매 요청 있음(아직 수락 전) → 소프트 삭제(숨김 처리)만 허용
- `예약중`, `판매완료` → 수정/삭제 자체를 막음

## 이유
- 대부분의 삭제는 "아직 아무도 관심 안 보인 상품을 내리는 것"이라,
  참조 무결성 문제가 없는 케이스가 대다수. 이 경우까지 소프트 삭제로
  처리하면 실제로 필요 없는 "숨김 상태"가 계속 쌓임.
- 구매 요청이 걸린 상품을 하드 삭제하면 PurchaseRequest/Transaction이
  존재하지 않는 상품을 참조하게 되어 참조 무결성이 깨짐 → 이 경우만
  소프트 삭제로 보호.
- 예약중/판매완료 상태에서 수정/삭제를 허용하면, 이미 확정된 거래의
  상품 정보(제목/가격 등)가 사후에 바뀌어버릴 수 있어 거래 기록의
  신뢰성이 깨짐.

## 트레이드오프
- 삭제 로직이 단순 소프트 삭제 하나로 처리하는 것보다 분기가 늘어나
  구현이 약간 더 복잡해짐 (상태 + 연관 데이터 존재 여부를 함께 체크).
- 다만 이 분기 자체가 도메인 규칙을 정확히 반영한 것이라, 오히려
  "왜 이렇게 구현했는지" 설명하기 좋은 지점이라고 판단.
