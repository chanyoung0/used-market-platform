# 0003. 프론트엔드 범위 결정

## 상태
확정

## 배경
백엔드 신입 지원용 포트폴리오 프로젝트로, 프론트엔드를 아예 안 만들지,
아니면 어느 정도까지 만들지 결정이 필요했음.

## 고민한 선택지
1. 프론트 없이 Swagger UI(springdoc-openapi)로만 API 검증/시연
2. MVP 핵심 흐름만 다루는 최소한의 프론트를 별도로 제작 (Claude Code 활용)
3. 디자인까지 신경 쓴 완성도 높은 프론트 제작

## 결정
2번 채택 — 로그인, 상품 목록/등록, 구매 요청/수락 정도의 핵심 흐름만
다루는 최소 프론트를 만들고, 디자인 완성도는 신경 쓰지 않는다.
Tier 2 기능(채팅, 찜하기 등)의 화면은 만들지 않는다.

## 이유
- 백엔드 신입 지원이 목표라, 평가받는 핵심은 API 설계·엔티티 관계·
  트랜잭션/동시성 처리 등 백엔드 역량. 프론트에 시간을 많이 쓰면
  상대적으로 백엔드에 쓸 시간이 줄어듦.
- Swagger 화면만으로는 실제 서비스가 동작하는 모습을 직관적으로
  보여주기 어려워, "돌아가는 화면"이 있는 편이 포트폴리오 임팩트
  면에서 유리하다고 판단.
- Claude Code를 활용해 프론트엔드 화면 뼈대(라우팅, API 연동 기본
  구조)를 빠르게 스캐폴딩. 생성된 코드는 직접 검토·수정하며 진행.

## 트레이드오프
- 백엔드 레포와 프론트 레포를 분리해서 관리 (README에 프론트
  레포 링크만 추가). 하나의 레포에 섞으면 백엔드 코드량/구조를
  파악하기 번거로워지기 때문.
