# 0009. 입력 검증 기준: DB 제약과 애플리케이션 검증의 이중 방어

## 상태
확정

## 배경
회원가입 요청에 검증이 없어서 빈 문자열 이메일/비밀번호도 저장되고, 필드가 누락되면 DB 제약 위반으로 500이 발생했음. 클라이언트 입력 문제가 서버 오류처럼 보이는 상태였고, 각 필드의 길이 기준도 정해져 있지 않았음(엔티티 컬럼은 기본값 255).

## 고민한 선택지
1. DB 제약(NOT NULL, UNIQUE, 길이)만 사용
2. 애플리케이션 검증(@Valid + Bean Validation)만 사용
3. 두 계층을 함께 사용하고, 필드별로 역할을 나눔

## 결정
3번 채택.
- 검증은 요청 DTO 필드의 제약 어노테이션과 Controller 파라미터의 @Valid로 수행하고, 이메일 중복처럼 DB 조회가 필요한 검증은 Service에서 수행함.
- 입력값이 그대로 컬럼에 저장되는 필드는 DTO의 @Size와 엔티티의 @Column(length)를 같은 값으로 맞춤.

| 필드 | DTO 검증 | 컬럼 |
|---|---|---|
| email | @NotBlank, @Email | 기본 255 (표준 최대 길이 254 이내) |
| nickname | @NotBlank, @Size(min = 2, max = 8) | length = 8 |
| password (평문 입력) | @NotBlank, @Size(min = 7, max = 18) | 해시 저장이므로 기본 255 유지 |

## 이유
- DB 제약은 어떤 경로로 데이터가 들어와도 지켜지는 마지막 방어선이지만, 위반이 500으로 드러나고 쿼리를 날린 뒤에야 실패함. 애플리케이션 검증은 잘못된 입력을 먼저 걸러 400으로 응답할 수 있음. 둘의 역할이 달라 하나로 대체되지 않음.
- 빈 문자열 금지, 이메일 형식 같은 규칙은 NOT NULL로 막을 수 없어 애플리케이션 계층이 담당해야 함.
- nickname은 화면에 그대로 노출되는 값이라 255자 허용은 부적절하다고 판단해 정책값(2~8자)을 정함. DTO와 컬럼을 같은 값으로 맞춰 검증은 통과했는데 DB에서 실패하는 틈을 없앰.
- password는 저장되는 값이 입력 평문이 아니라 BCrypt 해시(60자 고정)이므로 평문 길이와 컬럼 길이는 서로 영향을 주지 않음. 평문의 최대 길이는 BCrypt가 72바이트까지만 반영하는 점을 기준으로 정했고, 18자는 한글(글자당 3바이트)로 가정해도 54바이트라 한도 안에 들어옴.
- 검증 실패 응답은 ADR 0008의 INVALID_INPUT(400)으로 통일함.

## 트레이드오프
- 같은 규칙(nickname 2~8자)이 가입 DTO와 수정 DTO에 중복됨. 현재는 규칙이 두 개뿐이라 공통 상수로 분리하지 않고, 불일치가 실제 문제가 될 때 다시 판단함.
- password 최대 18자 제한은 긴 문장형 비밀번호를 쓰는 사용자를 제한함. MVP에서는 BCrypt 한도 안에서 단순한 기준을 택함.
- 로그인 DTO에는 가입 때의 @Size를 적용하지 않고 @NotBlank만 적용함. 정책이 바뀌기 전에 가입한 사용자가 로그인하지 못하는 상황을 막기 위함.
- ddl-auto=update는 이미 만들어진 컬럼의 길이 변경을 반영하지 않아, 길이를 바꿀 때 로컬에서는 테이블을 삭제 후 재생성해야 함. 배포 시점에 스키마 관리 방식을 재검토함.
- 수정 요청 DTO의 @Valid 연결은 해당 Controller 메서드를 구현하는 시점에 적용함.
