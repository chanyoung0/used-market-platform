# 0006. 패키지 구조: 계층형 대신 도메인형(Domain-driven) 채택

## 상태
확정

## 배경
프로젝트 초기 뼈대를 잡으면서, 패키지를 기술적 역할(Controller/Service/
Repository) 기준으로 나눌지, 도메인(Member/Product/Transaction) 기준으로
나눌지 결정이 필요했음.

## 고민한 선택지
1. 계층형 (Package by Layer): 최상위를 `controller/`, `service/`,
   `repository/`, `entity/`, `dto/`로 나누고, 그 안에 각 도메인 클래스를 배치
2. 도메인형 (Package by Feature): 최상위를 `domain/member/`,
   `domain/product/` 등 도메인 단위로 나누고, 그 안에서 계층을 구분

## 결정
2번(도메인형) 채택.

## 이유
- **응집도**: 한 도메인의 로직을 수정할 때 관련 파일(엔티티, 리포지토리,
  서비스, 컨트롤러)이 폴더 하나에 모여 있어, 여러 폴더를 오갈 필요가 없음.
  도메인이 3개 이상(Member/Product/Transaction)인 이 프로젝트 규모에서
  체감 차이가 큼.
- **결합도 파악 용이**: 패키지 간 의존 관계가 곧 도메인 간 의존 관계로
  드러남. 계층형은 특정 서비스가 다른 도메인의 리포지토리를 참조해도
  폴더 구조만으로는 드러나지 않아 import 문을 직접 확인해야 함.
- **확장 시 분리 용이**: 이후 도메인 단위로 서비스를 분리할 필요가
  생기면, 도메인형은 폴더 하나를 거의 그대로 떼어낼 수 있어 유리함.
  계층형은 한 도메인의 코드가 여러 폴더에 흩어져 있어 분리 작업이
  더 번거로움.

## 트레이드오프
- 여러 도메인이 공통으로 쓰는 로직(BaseEntity, 전역 예외처리, JWT 필터
  등)은 특정 도메인 폴더에 속하지 않으므로, 별도의 `global/` 패키지로
  분리해서 관리함.
- 도메인 간 경계가 모호한 클래스(예: Member와 Product 양쪽에 걸친
  Transaction 관련 로직)는 어느 도메인 폴더에 둘지 판단이 필요한 경우가
  생길 수 있음. 계층형에서는 이런 경계 고민 자체가 없음.
