# 0002. 구매 요청에 네고(가격 제안) 기능 포함

## 상태
확정

## 배경
구매 요청 기능을 설계하면서, 정가로만 구매 요청을 받을지
아니면 구매자가 희망 가격을 제시하는 네고 기능까지 포함할지 결정이 필요했음.

## 고민한 선택지
1. 정가 요청만 지원 (단순한 "구매하기" 버튼)
2. 네고(가격 제안) 포함, 판매자는 수락/거절만 가능
3. 네고 + 재협상까지 지원

## 결정
2번 채택 — 네고는 포함하되, 재협상은 MVP에서 제외.

## 이유
- 실제 중고거래 서비스(당근마켓 등)에서 "가격 제안"은 핵심 사용 패턴 중
  하나라, 이걸 빼면 도메인 모델링 관점에서 서비스의 특징이 드러나지 않는다고 판단.


- 재협상까지 넣으면 상태 전이(state)가 훨씬 복잡해짐
  (제안 → 재제안 → 재재제안 ... 무한 루프 가능성, 각 단계별 알림/만료 처리 등).
  MVP 범위에서 감당하기엔 복잡도 대비 학습 효과가 낮다고 판단해 제외.

## 트레이드오프 / 파생 이슈
- 한 상품에 여러 구매자가 동시에 네고 요청을 보낼 수 있음 → 판매자가 하나를
  수락하면 나머지 요청은 자동 거절되어야 하는데, 이 "동시 요청 처리"가
  동시성 문제로 이어짐 (두 요청이 거의 동시에 수락 처리를 시도하는 경우).
  이 이슈는 이후 별도 결정 기록(예: Redis 분산 락 도입)으로 다룰 예정 —
  MVP 단계에선 우선 단순한 비관적 락(DB 트랜잭션 레벨)으로 처리하고,
  트러블슈팅 사례로 발전시킬 계획.


- 실시간 채팅이 Tier 2로 분류되어 있어, 수락 이후 실제 만남 시간/장소를
  조율할 수단이 MVP엔 없음. 이 부분은 서비스 범위 밖으로 명시적으로
  제외하고, 거래 완료 처리는 판매자가 수동으로 진행하는 것으로 단순화함.
